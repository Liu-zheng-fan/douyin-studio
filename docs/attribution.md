# 三个来源项目的取舍

这套东西不是把三个仓库拼起来，而是**各取一层**。记录清楚为什么取、为什么不取，
免得后来的人以为有功能漏了。

## fy-code-animation（方法论层，取走最多）

**取走：**

| 内容 | 落在哪 |
|---|---|
| 「每镜必须有可观察的变化」判准 | `SKILL.md` 第 1 节、`studio/shots.py` 每个函数的 docstring |
| 语义关系 → 可视操作的映射（因果/对比/部分整体） | `shots.line`（因果路径）、`shots.split`（否定-肯定） |
| `motion-core` 的确定性数学 | `studio/motion.py` 全量移植为 Python |
| 确定性的硬要求（任意帧可 seek、无 wall clock、无隐藏状态） | `render.py` 的设计前提 |

**没取：**

- **341 风格库**：不随包分发，需要自备路径。缺它只影响「画风检索」，不影响方法论。
- **Remotion 落地代码**：需要 npm + 浏览器渲染，重量级；这里用 Pillow 直接出帧更轻。
- **四案音乐生成**：依赖 ACE-Step 本机模型，未接入；`bgm` 留成外部文件入口。

## EAC design world（概念层，只取形）

**取走：**

- 「镜头是资产」的思路 → 固化成七种可复用镜头类型，而不是一次性排版。
- 多轨时间线的组织方式 → 简化为「一镜一语音一画面」的顺序时间轴。
- 调色/示波器的工作流意识 → 未实现，只在 `theme.py` 里固定了对比度与文字描边。

**没取：**

整个插件（约 285 MB，React + Vite + Playwright，会改写 DSH 宿主界面）。
它适合「有真实素材要精剪」的场景；这条线是「无素材、纯代码画面」的轻量产线，
装进来只会增加两套渲染路径的冲突。

**什么时候该回头装 EAC**：当你有真实拍摄素材、需要转场/调色/多轨、或者需要导出剪映草稿给人工续剪时。

## bili-cli（契约层，只取规矩）

**取走：**

- stdout 只输出一个 JSON（`{"ok": true, "data": ...}` / `{"ok": false, "error": {...}}`）
- 写操作先 `--dry-run`
- 稳定的错误码，便于 Agent 分支处理
- 命令粒度：一个动作一条命令，不做交互式提示

**没取：**

- B 站相关的一切（登录、投稿、评论、私信、数据接口）——抖音场景用不上。
- `bili-cli` 本身作为依赖：Python 包名 `bili-agent`，与这条线无关。

## 新增的、三个项目都没有的部分

| 能力 | 为什么必须自己写 |
|---|---|
| 竖屏规范（安全区、字号、字幕位置） | 三个项目都不是抖音竖屏 |
| 合规检查（广告法词表 + AI 标识） | 企业号的硬约束，没人替你做 |
| 实验台账 + 单变量复盘 | 这是「持续变好」的唯一机制 |
| 人工发布包 | 抖音发布权限拿不到时的现实解法 |

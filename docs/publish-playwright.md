# 自动发布：可行路径与当前状态

**结论先说：本项目没有实现自动发布。** 这里记录的是从
`dsh-video-pipeline/skills/douyin-publish` 读到的真实做法，以及我们为什么先不做。

## 目前能做的

| 方式 | 状态 | 说明 |
|---|---|---|
| 人工发布包 | ✅ 已实现 | `python -m douyin publish package <dist>`，出成片+封面+文案+清单 |
| 官方开放平台 | ⚠️ 骨架 | `douyin/publish.py` 的 `api` 分支，需要「视频发布」权限 |
| 浏览器自动化 | ❌ 未实现 | 见下 |

## 浏览器自动化怎么做（读到的真实流程）

对方用的是 `playwright-cli` 驱动**真实 Chromium**，操作抖音创作者中心：

1. **持久化 profile**：`%USERPROFILE%\.cache\mimo-skills\douyin-publish\chrome-profile\`
   登录态（Cookie + localStorage）全在这个目录里，扫码一次可长期复用
2. **固定会话名**：`PLAYWRIGHT_CLI_SESSION=douyin-publish`
3. **流程**：open 上传页 → snapshot → 点「上传视频」→ 填绝对路径 → 填标题 → 设可见性 → 发布
4. **硬规则**（他们踩过坑总结的）：
   - 默认 headless，只有首次扫码开可见窗口
   - **每次操作前必须重新 snapshot**——ref 是动态的，禁止硬编码
   - 页面跳转后旧 ref 立即失效
   - 发布前让人确认标题与可见性

## 为什么我们没做

| 原因 | 说明 |
|---|---|
| 没有运行时 | 本机没装 Node/Playwright，装一套要下 Chromium（~150MB） |
| **无法验证** | 我拿不到你的扫码登录，写完也测不了，等于交付一个未验证的自动化 |
| 风控 | 自动化发布违反平台条款，封号风险由账号承担 |
| 责任 | 一条文案踩广告法，罚的是营业执照主体 |

## 什么时候值得做

当满足**全部三条**时再做：

1. 每天稳定产出 ≥1 条，人工发布的 30 秒成了瓶颈
2. 已有 ≥500 粉丝，封号代价需要认真对待
3. 愿意接受「页面改版就要修脚本」的维护成本

## 如果要做，顺序是

1. 先试**官方开放平台**（`publish.py --yes`）：合规、稳定，只是要审核
2. 审核不通过再考虑 Playwright：用独立 profile，**只用于发布，不复用日常浏览**
3. 无论哪条路，**发布前必须有人确认**——这一步不要省

# 为什么是现在这个样子

每个设计决定都记下来，包括**被否决的方案和原因**。
不写这个，三个月后没人（包括我自己）知道为什么代码长这样。

---

## 1. 为什么用 Pillow 逐帧，不用 Canvas / Remotion

**当时的约束**：本机没有 Chrome 自动化环境、没有 npm、只有 Python；要在一晚上做出第一条片子。

**Pillow 的收益**：零依赖、启动快、逐帧可控、确定性天然成立。

**代价（实测）**：帧差 4.58，实拍素材 33.64——**差 7.3 倍**。粒子、形变、3D 变换做不了。

**结论**：这不是"选错了"，是"先活下来"。但它是明确的技术债，写在
[known limits](#5-已知限制为什么不做) 里，不装作没有。

**什么时候该换**：当内容需要"画面本身在演"而不是"字在讲"时。换的时候只改
`render_frames()`，时间轴/音频/质检全不用动——它们只依赖"一串 PNG"。

## 2. 为什么时长由语音反推，而不是先定 30 秒

先定死时长，就要在录音后硬拉伸或截断，字幕必然错位。

现在的做法：TTS 出每句真实秒数 → 镜头时长 = 语音 + 0.18 前导 + 0.30 尾巴 → 字幕按标点切分、均匀铺在语音区间。

**副作用**：改一个字，全片时间轴重排。这正确——因为观众感知的是语速，不是秒数。

---

## 3. 为什么质检在审批之前

第一版顺序是「渲染 → 人看 → 有问题再改」。

问题：人会疲劳。一条"音轨静音"或"第一帧全黑"的片子占用你早上 10 秒注意力，
第二天你就不打开审批页了——**自动化就这样死的，不是死于技术**。

现在的顺序：`block` 级问题（黑帧、无音轨、尺寸错、超长、开场死帧）机器直接拦下，
根本进不了队列。人只看"技术上没问题、但我不喜欢"的那种判断。

---

## 4. 为什么拒绝必须选标签

最初只记"拒绝"，结果第二天还是同一个毛病——因为"不喜欢"不是一个可执行的信息。

现在六个标签各自映射到次日动作：

| 标签 | 次日改什么 |
|---|---|
| 选题不喜欢 | 换题材，优先补配额最低的那类 |
| 文案不像人 | 缩短句子、去书面词、加具体细节 |
| 画面丑 | 换背景 field / 换 art 风格 |
| 太慢 | 提高 drift，或砍一镜 |
| 音频难听 | 换音色别名 |
| 不想发这个产品 | 进黑名单 |

**连续两次同一标签 = 模板有病**，改模板不是改这条片。

## 5. 已知限制（为什么不做）

| 限制 | 为什么不做 |
|---|---|
| 只出竖屏 1080×1920 | 主战场是抖音；横屏是另一套版式，做了也用不上 |
| 不做自动发布 | 发布权限要资质；且违规罚的是营业执照主体，不是"AI 说错了" |
| 不接抖音官方数据 | 需要应用审核；现阶段的样本量还不值得为它等两周 |
| 不做真人出镜 | 没有摄像头，也没有你的手 |
| 不追求"完美" | 完美不可验证；能验证的是"这条比上条多知道一点" |

## 6. 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 一套 GUI 时间线（学 EAC） | 285 MB、改宿主界面；命令行场景下没人愿意拖时间轴 |
| 多模型接力写脚本（豆包初稿 + Gemini 精修） | 只有一个模型可用；而且多模型会让"哪一步变好了"无法归因 |
| 全自动发布（Playwright 驱动后台） | 风控风险高，封号代价大于效率收益 |
| 用现成 BGM 素材库 | 抖音曲库识别敏感；且压到 0.16 音量后只剩糊 |
| 用 SAPI 老音色 | 拼接式音色，一开口就掉完播率（实测主观差距极大） |
| 把所有能力做成一个巨型 SKILL.md | 上下文吃紧时会挤掉真正要执行的内容 |

---

## 7. 一条方法论

**确定性的部分写成代码，判断的部分写成文档。**

- 渲染、混音、质检 → 代码（要可复现）
- 选题、钩子、结构、审美 → 文档（要可讨论）

写反了就会变成：判断被硬编码进 if 里（改不动），渲染靠模型临场发挥（每次不一样）。
